# しりとりんご 企画・実装プラン

## 1. コンセプト

- 「しりとり」から始まるしりとりを、4択で5ステップ進める（1問目の定番の答えが「りんご」）。
- 正解は「みんなが一番選んだ答え」。自分の選択が多数派と一致するほど高得点。
- 選択肢・ルートはすべて事前に用意する（自由入力なし）。
- 全プレイヤーの選択を保存し、集計結果がそのまま「正解」になる。

## 2. ゲームの流れ

```
タイトル → Q1「しりとり → り？」4択 → Q2 … → Q5 → 結果画面（集計はここでまとめて表示）
```

1. 現在の単語と、その末尾の文字で始まる4つの候補を表示。
2. 1つ選ぶ → 回答を保存 → 選んだ単語が次の問題になる（途中では集計を見せない）。
3. 5ステップ終了で結果画面（たどったルート、各ステップの得票率、合計スコア）。

### ルール上の決め事
| 項目 | 方針 |
|---|---|
| 「ん」で終わる単語 | 選択肢に入れない |
| 長音「ー」 | 直前の母音で繋ぐ（例: パトカー → あ、スキー → い） |
| 小書き文字 | 大きい文字として扱う（例: ダチョウ → う、リュック → く） |
| 濁点・半濁点 | 変換しない（厳密一致）。データの検証で担保する |
| 同じ単語の再登場 | 1プレイ内では出さない（データの検証で保証、下記） |

## 3. データ構造（ルート）

### 案の比較
| 案 | 内容 | 必要な単語数（4択×5段） | 判断 |
|---|---|---|---|
| A. 完全な木 | 選択ごとに固有の分岐 | 4+16+64+256+1024 ≒ 1,360 | 手作業では不可能 |
| B. 単語ごとの4択 | 単語ごとに「次の4候補」を持つ | 合流次第で 60〜150 程度 | 合流させにくい |
| C. 末尾の文字ごとの4択 | 「末尾の文字 → 次の4択」の表。同じ文字で終わる単語からは同じ4択に合流する | 84語（21文字×4） | **採用** |

### データファイル
`backend/shiritori/routes.json`

```json
{
  "version": 1,
  "start": "しりとり",
  "maxSteps": 5,
  "choicesByKana": {
    "り": ["りんご", "りす", "リュック", "リコーダー"],
    "ご": ["ゴリラ", "ごま", "ごぼう", "ごみばこ"]
  }
}
```

- 選択肢を変えたら `version` を上げる。集計は version ごとに分かれる。
- しりとりは同じ文字に戻りやすい（ラッコ → コアラ → ラッコ）。末尾の文字ごとの表だとそのまま同じ単語が再登場するので、**全ルートを検証して、再登場が起きる単語を入れ替える**ことで防いでいる。
- 最初の回答（りんご → ゴリラ → ラッパ → パンダ → だるま）が選べるように作ってある。

### 検証（`python -m shiritori.validate`、テストでも実行）
- 各単語が表のキーの文字で始まる。
- 各文字の選択肢がちょうど4つ、「ん」で終わる単語がない。
- 開始から5ステップまでの全1,024ルートを列挙し、次の4択が存在する・同じ単語が2回出ないことを確認。
- 表にあるのに到達しない文字がない。

## 4. 保存・集計

SQLite に保存する（`backend/shiritori.db`、環境変数 `SHIRITORI_DB` で変更可）。追加の依存はなし（標準ライブラリの sqlite3）。

### テーブル
```sql
CREATE TABLE plays (
  id           TEXT PRIMARY KEY,   -- UUID
  player_id    TEXT NOT NULL,      -- 端末ごとの匿名ID（localStorage）
  data_version INTEGER NOT NULL,   -- routes.json の version
  status       TEXT NOT NULL,      -- playing / finished
  created_at   TEXT NOT NULL
);

CREATE TABLE answers (
  play_id    TEXT NOT NULL REFERENCES plays(id),
  step       INTEGER NOT NULL,     -- 1..5
  from_word  TEXT NOT NULL,        -- 出題された単語
  choice     TEXT NOT NULL,        -- 選んだ単語
  created_at TEXT NOT NULL,
  PRIMARY KEY (play_id, step)
);
CREATE INDEX idx_answers_node ON answers(from_word, choice);
```

### 集計
- 得票率 = その単語（`from_word`）で同じ `choice` を選んだ人数 ÷ その単語での総回答数。経路が違っても同じ単語に来た人の回答は合算する。
- 同一 `player_id` の同一単語への回答は、最初の1件だけ数える。2回目以降のプレイでは自分の選択が集計に入らないことがある。
- `data_version` が違う回答は混ぜない。
- 回答数が少ないときの「データ不足」表示は入れていない。代わりに各問の回答人数を表示している。

### 初期データ
- DB が空のとき、`backend/shiritori/seed.json` の1件（最初の回答）を投入する。

## 5. API（FastAPI、`/shiritori`）

| メソッド | パス | 内容 |
|---|---|---|
| POST | `/shiritori/plays` | `{player_id}` → プレイ開始。1問目の状態を返す |
| GET | `/shiritori/plays/{play_id}` | 現在の状態 |
| POST | `/shiritori/plays/{play_id}/answers` | `{step, choice}` → 次の問題の状態（最終問なら `finished: true`） |
| GET | `/shiritori/plays/{play_id}/result` | 各問の票数・得票率・1位かどうか、みんな度、1位一致数 |

状態（PlayState）: `{play_id, step, max_steps, history, word, kana, choices, finished}`

- 次の4択はサーバーが決める。フロントはしりとりのルールもデータも持たない。
- `step` が順番どおりでない、`choice` が4択にない、終了済みのプレイへの回答は 409。

## 6. フロントエンド（Next.js、`/shiritori`）

- `title`：遊び方、はじめる。
- `question`：ここまでの流れ、現在の単語、「○で始まるのは？」、4択ボタン。
- `result`：みんな度（得票率の平均）、1位と一致した数、各問の4択の得票率バー（自分の選択をハイライト）、回答人数。
- 匿名 `player_id` は初回に `crypto.randomUUID()` で生成して localStorage に保存。

## 7. 決定事項

1. 集計は最後にまとめて見せる（途中では見せない）。
2. 「ん」で終わる単語は選択肢に入れない。
3. 既存の Next.js + FastAPI に同居させる（`/shiritori`）。
4. 開始の単語は「しりとり」。最初の回答は りんご → ゴリラ → ラッパ → パンダ → だるま。

## 9. 残っている課題

- **選択肢の質**：同じ単語の再登場を避けるために入れ替えた結果、定番でない単語が混ざっている（例: ぎんか、ルームライト、まほうつかい）。
- **データの量**：84語なので、何度か遊ぶと同じ選択肢に当たる。
- **コールドスタート**：回答が少ないうちは1人の回答で100%になる。
- **不正対策**：匿名IDを消せば何度でも投票できる。デモ用途なので許容している。
