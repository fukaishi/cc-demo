# しりとりんご 企画・実装プラン

## 1. コンセプト

- 「りんご」から始まるしりとりを、4択で5ステップ進める。
- 正解は「みんなが一番選んだ答え」。自分の選択が多数派と一致するほど高得点。
- 選択肢・ルートはすべて事前に用意する（自由入力なし）。
- 全プレイヤーの選択を保存し、集計結果がそのまま「正解」になる。

## 2. ゲームの流れ

```
タイトル → Q1「りんご → ご？」4択 → Q2 … → Q5 → 結果画面（集計はここでまとめて表示）
```

1. 現在の単語と、その末尾の文字で始まる4つの候補を表示。
2. 1つ選ぶ → 回答を保存 → 選んだ単語が次の問題になる（途中では集計を見せない）。
3. 5ステップ終了で結果画面（たどったルート、各ステップの得票率、合計スコア）。

### ルール上の決め事
| 項目 | 方針 |
|---|---|
| 「ん」で終わる単語 | 選択肢に入れない |
| 長音「ー」 | 直前の母音で繋ぐ（例: ゴール → ル） |
| 小書き文字 | 大きい文字として扱う（例: きしゃ → や） |
| 濁点・半濁点 | 変換しない（厳密一致）。データ作成時の検証で担保する |
| 同じ単語の再登場 | 1プレイ内では出さない（データの段分けで保証、下記） |

## 3. データ構造（ルート）

### 案の比較
| 案 | 内容 | 必要な単語数（4択×5段） | 判断 |
|---|---|---|---|
| A. 完全な木 | 選択ごとに固有の分岐 | 4+16+64+256+1024 ≒ 1,360 | 手作業では不可能 |
| B. 単語グラフ | 単語ごとに「次の4候補」を1つだけ持つ。別ルートから同じ単語に合流してよい | 合流次第で 60〜150 程度 | **採用** |
| C. 一本道 | 何を選んでも次の問題は固定 | 20 | しりとりとして成立しない（選んでいない単語から続く）ので不採用 |

B を採用する。集計も「単語ノード × 選択肢」単位で行えるため、経路が違っても同じ単語に来た人のデータが合算され、サンプルが溜まりやすい。

### 実際の持ち方：末尾の文字ごとに4択（サンプルで採用）
単語ごとに `next` を書くと合流させにくく語数が増えるため、**「末尾の文字 → 次の4択」の表**にする。同じ文字で終わる単語からは同じ4択に自動で合流する。

ただしこのままだと「こま → まくら → ラッコ → こま」のように1プレイ内で同じ単語が再登場する。これを防ぐため、**段ごとに使う文字を分ける**。

| 出題 | 使う文字 | 各文字の4択の単語は何で終わるか |
|---|---|---|
| 1問目 | ご | 2問目の文字 |
| 2問目 | ら ま う こ | 3問目の文字 |
| 3問目 | ぱ だ す く と ぎ し た | 4・5問目の文字 |
| 4・5問目 | り る あ つ や い か き | 同じ段の**別の**文字 |

4・5問目は同じ文字集合を使い回すことで、表の数を 1+4+8+8 = 21 個（84語）に抑えている。
この構成で全1,024ルートに重複・「ん」終わりがないことを確認済み。

サンプル実装: `frontend/app/shiritori/routes.ts`（本実装では backend に移す）

### 検証スクリプト
データを増減したときの崩れを機械チェックする。
- 各単語が表のキーの文字で始まる（長音・小書きの正規化込み）。
- 各文字の選択肢がちょうど4つ、「ん」で終わる単語がない。
- 開始から5ステップまでの全ルートを列挙し、次の4択が存在する・同じ単語が2回出ないことを確認。
- 表にあるのに到達しない文字がない。

## 4. 保存・集計

既存の Todo API はインメモリなので、しりとりんごは **SQLite** に保存する（再起動で消えると集計の意味がない）。

### テーブル
```sql
CREATE TABLE plays (
  id          TEXT PRIMARY KEY,      -- UUID
  player_id   TEXT NOT NULL,         -- 端末ごとの匿名ID（localStorage）
  data_version INTEGER NOT NULL,     -- routes.json の version
  status      TEXT NOT NULL,         -- playing / finished / gameover
  created_at  TEXT NOT NULL
);

CREATE TABLE answers (
  play_id     TEXT NOT NULL REFERENCES plays(id),
  step        INTEGER NOT NULL,      -- 1..5
  from_word   TEXT NOT NULL,         -- 出題された単語
  choice      TEXT NOT NULL,         -- 選んだ単語
  created_at  TEXT NOT NULL,
  PRIMARY KEY (play_id, step)
);
CREATE INDEX idx_answers_node ON answers(from_word, choice);
```

### 集計
- 一致率 = そのノード（`from_word`）で同じ `choice` を選んだ人数 ÷ そのノードの総回答数。
- 自分の回答を含めるかは「含める」で統一（表示が0%にならない）。
- 回答数が少ないうちは数字に意味がないので、**n < 10 のときは「まだデータ不足」表示**にしてスコアに加算しない。
- `data_version` が変わって選択肢が変わったノードは、古いデータと混ぜない（集計クエリで version を絞る）。

### 不正・偏り対策（MVPでは最小限）
- 同一 `player_id` の同一ノードへの回答は、集計では最初の1件のみ数える。
- 認証はしない。匿名IDを消せば何度でも投票できるが、デモ用途なので許容。

## 5. API（FastAPI）

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/shiritori/routes` | routes.json を返す（フロントでグラフを保持） |
| POST | `/shiritori/plays` | `{player_id}` → `{play_id}` |
| POST | `/shiritori/plays/{play_id}/answers` | `{step, from_word, choice}` → そのノードの集計 `{total, counts: {単語: 件数}, my_rate}` |
| GET | `/shiritori/plays/{play_id}` | 結果画面用：ルートと各ステップの一致率・スコア |
| GET | `/shiritori/stats/{word}` | 任意ノードの集計（デバッグ・ランキング用） |

- サーバー側で `from_word` が現在のプレイの正しい位置か、`choice` が `next` に含まれるかを検証する（クライアントを信用しない）。
- 回答は各ステップで即保存する。途中離脱したプレイの回答も集計に使える。

## 6. フロントエンド（Next.js）

画面は1ページ内の状態遷移で足りる。
- `title`：スタートボタン、遊び方。
- `question`：現在の単語（大きく）、「ステップ n/5」、4択ボタン。
- `result`：みんな度（一致率の平均）、1位と一致した数、各ステップの4択の得票率バー（自分の選択をハイライト）、「もう一度」。

状態は `useReducer` で `{phase, playId, step, currentWord, history[]}` を管理。匿名 `player_id` は初回に `crypto.randomUUID()` で生成して localStorage に保存。

### スコア
- 各ステップ：自分の選択の一致率（0〜100）。
- 合計：5ステップの平均を「みんな度 ○○%」として表示。

## 8. リスク・未決事項

- **データ作成の量**：4択×5段は合流させても単語数が多い。最初は「4択×3段」で作り、検証スクリプトが通る状態で段数を伸ばす方が安全。
- **コールドスタート**：公開直後は回答数ゼロで「みんなの答え」が存在しない。対策候補：(a) データ不足表示で割り切る、(b) 作成者の想定多数派を初期票として数件入れる。(b) は結果を歪めるので、入れるなら集計画面で区別する。
- **選択肢の偏り**：4択のうち明らかな本命が1つあると一致率が常に高く、ゲーム性が落ちる。データ作成時に「本命が割れそうな4つ」を意識する必要がある（これはデータ品質の問題でコードでは解決しない）。
- **表記ゆれ**：カタカナ/ひらがなの表示と `reading` を分けて持つことで対応。漢字は使わない方針でよいか要確認。

## 9. 決定事項

1. 集計は最後にまとめて見せる（途中では見せない）。
2. 「ん」で終わる単語は選択肢に入れない。
3. 既存の Next.js + FastAPI に同居させる（`/shiritori`）。
